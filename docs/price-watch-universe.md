## 0b. 帰属プロトコル v2「受益カード」（2026-07-28・2AI独立設計の一致部を凍結）

> 商品→銘柄の紐付け（帰属）の正本ルール。設計= Fable5(effort:high)×GPT5.6 Sol の独立2案が
> 同型に収束（一致8点・割れ1点はユーザー裁定でA案）。実装= configs/price_universe_sources.json v2
> （銘柄ごとの受益カード）+ price_universe_check.py（表示/STALE）+ price_watch_forward.py（記録フィルタ）。

**カード必須原則**: 受益銘柄は1社ずつカード（btype=3類型・sign・evidence・verified・tier）を持つ。
**カードが書けない銘柄は台帳に載せない**（誤帰属3件は全部「理由を書けと言われたら書けなかった
エントリ」だった）。rejected も理由つきで残す＝再提案ループ防止。

**5関門**（新商品・新銘柄の帰属はすべてこの順で審査）:

1. **関門B TOP1000照合（機械）**: master と照合し圏外は即棄却。圏外しか受益者がいなければ
   `受益者なし`＝発火記録のみ。**「代わりに近い大手」を後付けで書くの禁止**（米/卵事故の逆流防止）
2. **関門A 符号一文宣言（人間確定）**: 「この商材価格は当該社P/Lの**売上単価/在庫評価**に入るか
   **売上原価**に入るか」を一文で書く。原価なら sign=−（逆シグナル用に残すのは可）。
   一次産品はデフォルト「買い手」と推定し、受益主張側が3類型（§0）で反証して初めて覆る
3. **関門C 1ホップ制限**: 商材価格が売上単価・保有評価に直接入るもののみ。所得・需要を経由する
   2ホップ（米→農家所得→農機）は一律棄却。例外だった代替品受益（不二製油型）は唯一の実例が2026-08-03に却下され**現在実例ゼロ**（規則自体は残すが、採用には決算実読で符号確認が必須）
4. **関門D 桁チェック**: 「商材+10%→営業利益+2%以上」を式1本で書けるか。書けなければ細すぎ棄却
5. **証拠序列**: E1会社開示の感応度 ＞ E2有報セグメント利益(目安30%以上) ＞ E4経営者言及 ＞
   E3過去株価実測(補強のみ・単独採用禁止=データマイニング防止) ＞ E5「関連銘柄」記事(証拠ゼロ点・
   候補発見のみ)。confirmed には E1/E2 が1つ以上必要。型合格だが証拠未取得は provisional(仮)

## 16a. 品薄→受益銘柄の対応表（2026-07-28 新設・Xレーンの銘柄特定）

正本 = `configs/x_shortage_map.json`（読み込み・自己検証・表示は `scripts/x_shortage_map.py`）。
それまで X レーンは発火しても銘柄を一切出せなかった（`price_watch_alert.py` に
「銘柄未特定（Xレーンは候補生成）」と書かれていた）。ここを §0b と同じ規律で埋めたもの。

**なぜ品薄レーンが要るのか**: 商品価格レーンの受益対象は TOP1000中92社（9.4%）で頭打ちになる。
日本の大型株は資源を掘る側ではなく「**品薄になった物を作る機械・部材・材料**」を作る側に厚い
（台帳で pin に半導体を含む会社が56社・volume型627社のうち自社製品の需給で動くものが397社）。
品薄を入口にすると、価格を入口にしたときに届かない層へ届く。

### 品薄の7分類（混ぜると符号を取り違える）

| type | 意味 | 銘柄を出す | 小売が受益側に立てるか |
|---|---|:-:|:-:|
| `price` | スポット価格が公表され品薄が即座に単価へ乗る | ✅ | ✗ |
| `capex` | 品薄が増産投資を呼び装置・材料に発注（数四半期遅れ） | ✅ | ✗ |
| `demand` | **需要急増**による品薄。値引き縮小＋数量増 | ✅ | **✅（この型のみ）** |
| `secondary` | 定価固定の品薄で、プレミアムを取る二次流通側が受益 | ✅ | ✗（layer=secondary） |
| `resale` | 定価固定でプレミアムがメーカーに1円も届かない | ✗ | — |
| `disruption` | 供給断絶。需要増ではなく復旧で終わる | ✗ | — |
| `broad` | 主題が特定できない汎用クエリ | ✗ | — |

**最大の落とし穴は `resale`**。X で最も目立つ品薄（ゲーム機・トレカ・フィギュアのプレ値）は、
メーカーが定価で卸している限り売上単価が動かないため株に効かない。ここで銘柄を出すのが最悪の誤り。
**`demand` と供給制約型の分離**も必須で、小売は「需要急増で売り切れ」なら受益、「仕入れられない」なら
減益と符号が真逆になる（この区別が無いと家電量販が誤って買い候補に出る）。

### 規約（機械強制・`scripts/x_shortage_map.py` の validate が全部を検査）

1. **関門B**: `code` は `data/center_pin/center_pin.jsonl`（TOP1000）に実在必須。`name` も台帳と完全一致
2. `actionable` = 型の actionable **かつ** 受益カード非空。型が対象でも TOP1000内に受益銘柄が
   居なければ非対象（木材・米・バイクが該当。**無理に銘柄を立てない**）
3. `tier: confirmed` は center_pin の `pin` が当該生産連鎖を明示している場合のみ。他は `provisional`(仮)。
   `verified` から12ヶ月超は STALE 表示
4. `layer=user`（買って使う側）は sign=+ を名乗れない。`layer=retail` は `demand` 型のみ、
   `layer=secondary` は `secondary` 型のみ sign=+ 可
5. `traps`（sign=-）と `dormant_beneficiaries`（分類が覆った時の再利用候補）は捨てずに残す
6. **検証エラー時は銘柄を一切出さない**（`price_watch_alert.load_shortage_map` が None を返す）＝
   誤帰属より沈黙を選ぶ

### 売値 vs 原価の正味検証（2026-07-29・全72社・ユーザー指摘による第2の関門）

前節（セグメント裏取り）は「**売る側の規模**」しか見ていなかった。ユーザー指摘:

> 決算書を読めばメイン商材と原材料のメインが分かるのでは？
> そこが品薄になれば売上が上がるけど、**原価が上がると意味がない**という検証をすればよいのでは？

全72社の決算から「**売る物**」と「**買う物（主要原材料）**」を両方抽出し、原価率・会社開示の
営業利益増減ブリッジと合わせて**正味（売値効果−原価効果）**で再判定した。

#### linkage（品薄・値上がり時の構造）

| linkage | 意味 | 社数 |
|---|---|--:|
| `net_positive` | 売値は上がるが**原材料は連動しない** → 素直に増益 | 24 |
| `offset` | **売値上昇の原因が原材料高そのもの**。値上げは転嫁で相殺 | 25 |
| `spread` | 売値も原価も同じ市況で動く。差でしか儲からない | 19 |
| `unclear` | 開示不足 | 4 |

### 誤検出対策（実測21,933件＋実収集で検証）

1. **境界規則** — カタカナ社名の前後がカタカナなら別語。これだけで誤ヒット 13,435→11,170 に減り、
   「エン」(4849・565件がエンジニア等)「フジ」(8278・574件がフジクラ等)が全消滅
2. **最長一致優先** — 「ソフトバンクグループ」を「ソフトバンク」で二重計上しない
3. **2文字以下の社名は不採用** / **裸の4桁コードは不採用**（`(9509)` 形式のみ）
4. **短縮形ブロック** — 接尾辞を落とすと一般語になるものは短縮形だけ止める（正式名とコード表記は有効）。
   プレミア／ストライク／トモニ／アサヒ／ヤマダ 等

**重要な教訓**: 株クラスタ21,933件のコーパスでは誤検出ゼロだったのに、実収集の消費者投稿で
**「プレミア価格を覚悟してましたが…」がプレミアグループ(7199)に誤マッチした**。
この辞書が読むのは株の投稿ではなく**消費者の投稿**なので、株コーパスだけで検証すると必ず外す。

1. **見逃し（重大）**: zスコアのベースラインに「言及ゼロの日」が入っていなかった。
   台帳は言及があった日しか行を持たないため、**たまにしか名前が出ない銘柄は
   baseline_days 不足で永久に warmup のまま固定**され、急増しても鳴らなかった
   （実測: 14日中3日しか言及が無い銘柄が20件に急増しても `warmup` のまま）。
   → 「その日を処理した」印の行（`code="__scanned__"`）を必ず残し、
   処理済みの日は言及ゼロなら 0 として数えるようにした。修正後は z=21.66 で `alert`
2. **鳴りすぎ（1の修正で新たに開いた穴）**: ベースラインを0で埋めた結果、大半の銘柄で
   標準偏差が0になり、**ゼロが続いた後の「たった1件」でも sigma0_jump として発火**するようになった。
   → `MIN_COUNT_FOR_ALERT = 3` を追加。1件では鳴らず3件で鳴る

固定テスト4ケース: ゼロ続き→1件=鳴らない／ゼロ続き→3件=鳴る／たまに言及→20件=鳴る／平常運転=鳴らない。

## 16n. 言及レーンの「同日複数回収集」汚染を封鎖（2026-08-03）

**発端は私（AI）の誤報**: 「昨晩22:10のX収集が欠測」と報告したが誤り。台帳の `date` は
**収集対象UTC日**（実行日の前日）なので「最新 date が前日」は正常状態であり、欠測ではない
（8/1分50行の `run_at` はすべて `2026-08-02T13:10 UTC`＝まさに定時実行）。誤読の中身は
①`date`と実行日の1日ズレを欠測と解釈 ②`launchctl runs=0` を証拠に採用（今朝10:27の再起動で
カウンタがリセットされただけ）③pmset の MaintenanceWake をスリープの証拠と誤読（8/2 は
Entering Sleep が0件）。3レンズの独立検証で反証済み。**再発防止の教訓＝「最新dateが前日」は
このシステムの正常形。欠測判定は `run_at` と launchd の StandardOutPath ログで行う**。

**その調査で見つかった実在の不具合**: 言及レーン（§16c）は `texts/<day>.jsonl` を
**全実行の和集合**で読んでいた。同じ日を手動で追加収集すると母集団そのものが膨らみ、
その日だけ言及数が水増しされて zスコアのベースラインが歪む。

- 実測: 2026-07-31 は5回収集（本文2007行）→ 言及 **125件・63銘柄**。他日は76〜95件・41〜53銘柄で、
  **その日だけが外れ値**になっていた
- 件数レーン（`price_watch_alert.judge` の `by_date`）は「同一 date は最後の clean 行だけ採る」＝
  1日1標本で既に守られていた。**言及レーンだけが未対応**だった
- 修正: `x_mention_extract.canonical_run()` を新設し、**その日の代表となる1回分だけ**を判定に使う。
  代表＝**網羅クエリ数が最多の実行**（同数なら後の実行）で、網羅数は収集台帳の clean 定義
  （`run_quality()`＝status ok・非censored・count有）で測る＝件数レーンと**同じ品質定義を共有**する
- **時刻だけで「最後」を採ってはいけない**（Codex敵対レビュー CONFIRMED）: collector は
  `--queries` で一部クエリのみの実行を正式に許可しており、完全実行の後に2クエリだけの手動実行が
  あると、最後を採る規約では**残り48クエリを丸ごと言及ゼロとして記録**してしまう（＝偽の低ベースライン
  →後日の偽陽性）。実データにも 2026-07-31 に「42ク完全→3→3→2→50ク完全」の並びが実在した
- 併せて: run_at は文字列 max でなく**時刻として比較**（TZ表記の揺れで壊れるため）／`run_at` 欠損行が
  混ざる日は畳まないが複数実行なら警告を出す／捨てた行数と選定理由を必ず標準出力に出す／
  `--rebuild` 時に発火台帳が存在すれば「過去の発火は再整合しない」と警告。回帰テスト**7件**を `--selftest` に内蔵
- 是正結果（`--rebuild`）: 2026-07-31 が **125→94件・63→53銘柄** に是正され他日と同水準へ。
  他の4日は完全に不変（7/28も33行を除外したが言及結果は同一）。zスコアは「今日 vs 過去14日」の
  比較なので、日ごとに収集回数が違うと判定が壊れる——取りこぼしより**日間の比較可能性**を優先する

## 16o. 検出器を「単日z」から「波」へ（2026-08-04・型と検出器の不一致を解消）

敵対クロスレビューの一致指摘（§16n の次）: **§16i で自分が言語化した境界条件「単日zでなく複数週の
持続的増加で判定すべき」がコードに実装されていなかった**（grep 0件）。実証済みの型は「投稿が数週間で
3〜10倍に膨らむ」なのに、検出器は「1日のz」を見ていた。2026-08-02 の初の本番発火（銅 z=3.57）も、
買うと逆効果だった原油（2026-03・単月スパイク）と**判定形式が同一**だった。

**較正（backfill の実日次件数・成立4 vs 非成立4）**:

| ルール | 陽性（銅/レアメタル/HDD/メモリ） | 陰性（金/原油/ポケカ/中古車） |
|---|:--:|:--:|
| 単日 z>=3.0（v1・従来） | 3/4 | **3/4 誤発火**（判別力ほぼ無し） |
| 単日 z + 最小件数10 | 3/4 | 3/4 |
| 14日内に z>=3 が2回（持続） | 2/4 | 2/4 |
| **28日平均 ÷ 前28日平均 >= 2.0 かつ当日>=10件（v2）** | **4/4** | **0/4** |

- 発火日も実用的: レアメタル **2026-01-14**（後ろ向き検証の「1/15買い→4戦4勝・平均+30.8pt」と一致）・
  メモリ 2025-10-21・銅 2025-10-07・HDD 2025-11-01
- **閾値の局所安定性**: 倍率1.75〜2.0 × 窓21/28/35日 のどの組合せでも 4/4 vs 0/4。1.5に緩めると
  陰性2/4が誤発火。ただしこれは「1点狙いではない」ことの証拠であって、**過適合の否定にはならない**
  （Codex S-7）: 8系列を見た後にルール族自体を選んでおり、陽性4・陰性4しかなく、金とポケカは
  どちらも「飽和語」で生成機序が重複しうる。**holdout系列は無い**。したがって v2 の真の評価は
  前向き（2026-08-30以降の実運用）でしか得られない——後ろ向きの4/4は「v1より悪くないことの
  最低限の確認」であって性能の証明ではない、と位置づける
- 実装した `judge_query` 自体を過去データに通して **4/4 vs 0/4 を再現確認**（分析スクリプトと実装のズレ無し）

**実装**（`price_watch_alert.py` / `configs/x_price_watch.json`）:
- `alert`（発火・台帳と通知に出る）= 波条件 かつ 当日件数>=`min_abs_count`(10)。**単日zは不要**
  （ゆっくり膨らむ本物の波を取り逃がさないため）
- `watch`（候補・表示のみ）= 単日 z>=3.0 だが波が未成立/履歴不足。**台帳にも通知にも出さない**
- 最小件数の床は低λクエリ対策（平時1〜2件のクエリは Poisson の離散性だけで z>=3 に届き、
  実測ベースで年62件規模の誤発火が見込まれていた）
- `RULE_VERSION = "v2-wave28x2"` を前向き記録に刻む。**v1の発火（8/2の銅ほか）は消さずv1として据え置き**、
  検定では版をまたいで混ぜない

**運用上の帰結（重要）**: 波の判定には前窓（28〜56日前）に十分な標本が要る。現行台帳は
2026-07-25 開始なので、標本数バランス条件（prev>=cur*0.3）込みで **v2 が発火しうるのは
2026-08-30 ごろから**（前窓に3標本入るだけなら 08-24 だが、3標本の平均と28標本の平均を
比べることになるため balance で抑止する）。前窓が満杯（28標本）になるのは 09-19。
それまで全クエリは「候補」表示に留まる＝静かになるのは仕様（誤発火を年62件規模→ほぼ0に
落とした代償として、当面は取りこぼしも増える）。8/2の銅は v2 では候補（履歴不足）。

**当日を直近窓に含めることの検証**: 自己参照（当日の跳びが自分の判定を押し上げる）を疑い、
当日を除いた場合と比較したが、除くと陽性3/4に落ち（銅を取り逃す）陰性は0/4のまま＝

2.0倍に届かないため構造的にも安全。**含める**を採用。

## 16w. 海外上場銘柄の受益カード（2026-08-17 オーナー裁定 P-08c「海外も入れる」）

§16v の初回適用で、**ホエイ高騰の受益者は日本株に不在・海外上場（Glanbia plc）に実在**することが判明した
（同型: リチウム・カカオ・コーヒー等、商品の供給ショックは受益者が海外に偏る構造）。
オーナー裁定により、受益カードの帰属先に**海外上場銘柄を認める**。ただし既存の検定を汚さないため境界を固定する。

### 入場条件（4つとも満たす）

1. **関門は日本株と同一**（§0b 5関門・決算実読・**営業利益構成比 ≥30% で confirmed**／売上比率だけなら provisional 止まり）。
   業種名や知名度からの推定は日本株と同様に禁止
2. **カードに市場を明示**: `market`（既定 `"JP"`）。`JP` 以外は **`ticker`（価格取得に使う記号）と
   `benchmark`（超過リターンの基準指数）を必須**とする。欠けたカードは fail-closed で発火対象から外す
3. **評価レーンを分離**: 既存の前向き検定（事前登録・対TOPIX超過・n≥100）に**海外株を混ぜない**。
   日本株と海外株では基準指数も営業日も違い、同じ分母に入れると検定が壊れる
   （ピークアウト §16j・浸透 §16v と同じレーン分離の裁定）。海外は自国指数超過で別台帳に記録する
4. **通知には市場を表示**（例 `[IE] Glanbia`）。どの市場の銘柄かが分からない通知を出さない

### 非ゴール

- 海外株の**自動売買・実弾**は対象外（本レーンはペーパー前向き記録のみ）
- 海外株ユニバースの網羅（TOP1000 相当の台帳作り）はしない。**受益カードとして関門を通った銘柄だけ**を持つ
  ＝「日本株で拾えないから海外を広く漁る」ではなく「商品ごとに受益者を1枚ずつ確かめる」の延長

ある。受益（買い）は出せないが、**保有銘柄への逆風（コスト警報）としては機能する**（天然ゴム↑＝タイヤ4社の原価増、
木材↑＝住宅3社の原価増）。買いシグナルと逆風警報を混同しないよう、カードは sign=− のまま置き、
発火時の表示は「受益者なし」を維持する（§0b 関門Bの逆流防止）。
