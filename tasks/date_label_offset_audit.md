# 収集日ラベルと投稿実時刻のずれ — X 収集レーン横断の棚卸し（2026-08-10）

**きっかけ**: せどりトレンド週次の実走中に `2026-08-03.jsonl` の162件すべてが 08-04 の投稿だと判明
（→ `tasks/sedori_keyword_review.md` §7）。同じ collector を使う x_price_watch 系にも同じずれがあるか、
判定や対外的な日付主張が汚れていないかを棚卸しした。

**結論（先に）**: ずれは実在し、**x_price_watch では投稿の 59.8% が「ラベル+1日」に発生**していた。
ただし **z スコアの急増検知そのものは壊れていない**（全日が同じ構造でずれているため相対比較は成立）。
**壊れるのは株価との突き合わせ**（`price_linkage` / `evaluate_alerts`）で、基準日が実際の投稿日より
前に置かれるため「言及後に上がった」が**投稿当日の同時進行の値動きを含む**。幸い evaluation 行は
まだ 0 件で、**取り下げるべき既存結論は無い**（＝事前に捕まえた）。

## 1. 実測（JST基準・市場日と揃える）

| レーン | n（posted_at あり） | ラベル日と同じ | **ラベル+1日** | ラベル-1日以前 |
|---|---:|---:|---:|---:|
| `data/x_price_watch/texts/`（12日分） | 12,186 | 4,902（40.2%） | **7,284（59.8%）** | 0 |
| `data/sedori_trend/texts/`（8日分） | 1,483 | 115（7.8%） | **1,368（92.2%）** | 0 |

- **過去方向への漏れは 0 件**（ラベルより前の投稿は入っていない）
- 各ファイルの実時刻レンジは概ね **UTC (D-1)T15:00 〜 (D+1)T13:4x**
  ＝ **JST D 00:00 〜 D+1 22:4x**（＝収集実行時刻 22:10 JST に張り付いて終わる）
- sedori のずれが極端（92.2%）なのは、スクロール上限（`max_scrolls` 15・`cap_posts` 200）で
  **窓の新しい側だけを収穫して打ち切る**ため。窓が広いほど新しい側＝翌日に偏る

### 原因

`scripts/price_watch_collect.py:76` が `since:{D} until:{D+1}` を組む。X の日付演算子は
**ログイン中アカウントのタイムゾーンで解釈され、`until:` はその日を含む**ため、
意図した「JST D の1日」ではなく **JST D 00:00 〜 D+1 いっぱい（実際は実行時刻まで）の約2日窓**になる。
`scripts/price_watch_collect.py:60-66` の `target_utc_day()`（前UTC日）は正しく動いており、
ずれは UTC/JST の取り違えではなく **`until:` の包含 + アカウントTZ解釈**が原因。

### 副次発見: 窓の意味がアカウント任せで、しかも記録されていない

`2026-08-07.jsonl` だけ窓が **UTC 08-07 の丸1日**（他の日は上記の JST 2日窓）。
タイムスタンプは秒までばらけており捏造ではない（実データ）。日付演算子の解釈が
**その時ログインしていたアカウントのTZ設定に依存する**ため、別アカウント/別セッションで
走ると窓の意味が変わる。ところが `ledger.jsonl` のフィールドは
`date/query_id/lane/config_version/run_at/count/censored/scrolls/status/samples/elapsed_sec` で
**使用プロファイル・アカウントを記録していない**（`price_watch_collect.py:198-207` は stdout に出すだけ）。
→ 後から「この日の窓はどの意味だったか」を検証できない。既知の再発パターン
`identity-verify-before-use` の同型。

## 3. 何が壊れるか（具体）

`price_linkage(code, mention_date)` は基準日を「**ラベル日以前**の直近営業日終値」に置く。
投稿の 59.8%（sedori は 92.2%）は実際には**ラベル+1日**に出ているので:

- 基準日は「投稿がまだ存在しない時点」の終値になる
- 測定窓が **投稿当日そのものの値動きを内包する**
- 結果、「言及後に株価が上がった」は**予測ではなく同時進行の相関**を混ぜた数字になる
- 実務上も再現不能: ラベル日の終値で買うには、翌日の投稿を知っている必要がある（look-ahead）

**現状の被害**: `data/x_price_watch/mention_alerts.jsonl` は 17 行すべて alert 行のみで
**`type=evaluation` の行は 0 件**（+5営業日が未到来）。よって
**取り下げ・訂正が必要な既存の結論は無い**。今のうちに直せば損失ゼロで済む。

**正本側の記述**: `docs/price-watch-universe.md:1139-1141`（`price_linkage` の説明）と
`:1156`（「連動して上がっている」の機械判定）、`:1166-1169`（固定窓評価）は
いずれも「言及日」を実投稿日と同一視した書き方になっており、この棚卸しの結果を反映する必要がある。

## 4. 採用した直し方 = **A（2026-08-10 実装済み）**

B は `query_sha` が変わり凍結ベースラインが全リセット、C は look-ahead 放置なので、
比較する余地がない（＝ユーザー裁定を挟まず A を実装した）。

**実装**:
- `x_mention_extract.post_date_jst_max(day, code=None)` 新設 … 収集日ラベルの本文から
  実投稿日（JST）の最大値を返す。銘柄指定時は羅列ガード（`MAX_CODES_PER_POST`）を judge と
  同じ扱いで適用してから、その銘柄に言及した投稿だけを見る
- `effective_base_date(day, code=None)` … 実投稿日が取れればそれ、取れなければ**ラベル日にフォールバック**
  （ラベル日基準は実投稿より前＝甘い側なので、取れた時だけ厳しい側に寄せる。古いデータで
  従来より甘い判定に倒さない）
- 発火時（`:549`）と固定窓評価（`:430`）の両方が `effective_base_date()` を使う。
  台帳（`mention_alerts.jsonl`）の alert 行・evaluation 行の両方に **`post_date_jst`** を残し、
  後段が同じ基準日を再現できるようにした（古い行に無い場合は texts から引き直す）
- `price_watch_collect.py` の ledger 行に **`profile` / `expected_handle`** を追加
  （窓の意味がアカウントTZ依存なので、後から検証できるようにする）
- 固定テスト3件を `x_mention_extract.py --selftest` に追加（実投稿日=JST最大を採る／texts 不在時の
  フォールバック／銘柄指定時に非言及投稿を含めない）。**既存12件と合わせて全通過**

**実測の効果**: 既存 alert 17件すべてで基準日が **+1日** 動いた（100%）。
ラベル日基準は例外的な事故ではなく**全件で look-ahead していた**。

|---|---|---|

| 2026-08-05 | ユニチカ・任天堂・ＪＸ金属・三井化学・アルコニックス・太陽誘電・ソフトバンクG | 2026-08-06 |
| 2026-08-06 | レーザーテック・フジクラ | 2026-08-07 |

**残（別途）**: 収集窓自体を1日に狭める案 B は採らなかったので、**z スコアの帰属日は引き続き
「ラベル日」で、実際の投稿は+1日寄り**。急増検知の相対比較は成立しているので実害はないが、
発火日を人に伝える時はこのずれを踏まえる（正本はこのファイル）。

## 付録: 検討して採らなかった案

| 案 | 内容 | 不採用の理由 |

| **B** | 収集クエリの窓を実1日に直す（`until:` の包含とTZを踏まえた指定に変更） | 根本原因は消えるが、**クエリ文字列が変わる＝`query_sha` が変わり `price_watch_alert.py:181` の凍結ベースラインが全リセット**（再ウォームアップ7日以上・過去14日との比較が途切れる）。検知を止めてまで払うコストではない |
